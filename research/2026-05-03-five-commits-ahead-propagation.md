## What I found

### Finding 1 — the wrong number entered the journal ~37 hours BEFORE auditor-4

The sweep located the wrong number first at auditor-4 (2026-05-02 00:05, JOURNAL.md:620). It actually appeared earlier:

| When | Where | Quote |
|---|---|---|
| 2026-05-01 11:00 | worker-11am, JOURNAL.md:564 | "origin/main = `ae7d9fd…` (5 commits behind local; not pushed per CLAUDE.md / role spec)" |
| 2026-05-01 12:00 | worker-12pm, JOURNAL.md:581 | "`origin/main` = `ae7d9fd…` (5 commits behind local; not pushed per `roles/worker.md` and `CLAUDE.md`)" |
| 2026-05-02 00:05 | night-auditor, JOURNAL.md:620 | "Local HEAD `f6fbb7e` is 5 commits ahead of `origin/main` (`ae7d9fd`)" |

At 2026-05-01 11:00, worker-8am had just made one commit (f6fbb7e, parent ae7d9fd) — HEAD was 1 ahead, not 5. The worker did not run `git rev-list --count`; the number was not generated by the bash command they cited (or rather: the field is in the "verified" block but the underlying command, if run, would have returned 1). Worker-12pm copied worker-11am's framing verbatim. Auditor-4 then re-cited "5 commits ahead" in a structurally similar slot in a different role's entry.

**Implication for the sweep's analysis:** the sweep's likely-cognitive-source theory ("4 worker JOURNAL appends + 1 digest = 5 uncommitted journal entries since the last state-file commit") cannot be the source — at 2026-05-01 11:00, only 3 journal entries had accumulated since the f6fbb7e commit (worker-8am's own entry post-commit + worker-9am + worker-10am, all 2026-05-01). The "5" number had to come from elsewhere, and worker-11am is the entry where it first appeared.

**Eight consecutive runs since the corrective grounded their commit-distance claim in `git rev-list --count origin/main..HEAD` directly and got the right answer.** The wrong number is currently isolated to the three entries listed in Finding 1, all on disk, none referenced as authoritative anywhere downstream.

### Finding 3 — digest 2026-05-01 16:45 did NOT propagate the wrong number, but also did NOT catch it

Digest 2026-05-01 16:45 (line 594 of JOURNAL.md, plus `digests/2026-05-01.md`) does not cite a commit-ahead/behind count at all — neither right nor wrong. The closest mentions are: "worker-8am made one bookkeeping commit (`f6fbb7e`)" (right), and "Five Worker shifts produced JOURNAL appends only" (right, references shift count not commit count). The digest's silence on the specific number is what kept it out of the propagation chain — but that silence also means there was no opportunity for the digest to catch the wrong number at the moment it was already on disk in worker-11am and worker-12pm above.

### Finding 4 — STATE.md "Known constraints" is the durable corrective anchor

The planner-7:10 2026-05-02 STATE.md write put the corrected statement into the file every downstream role reads first. Every worker on 2026-05-02 cited STATE.md "Known constraints" by name when verifying the count. The audit-quality concern that the sweep flagged gets a partial vindication here: when STATE.md carries a precise refutation with the bash command that produced the right number, downstream consumers DO read it and DO re-verify. The corrective worked because the planner did exactly what yesterday's researcher's recommendation #1 proposed (numeric self-consistency check, with the bash command output captured in-line). This is empirical evidence that the cowork-session 2026-04-30 PROPOSED entry's amendments — particularly numeric self-consistency — would catch this class of failure if applied at the auditor level.

### Finding 5 — likely cognitive source for worker-11am's original "5"

The sweep proposed "4 workers + 1 digest = 5 uncommitted entries" as the cognitive source for auditor-4. That theory cannot apply to worker-11am 2026-05-01 11:00 (only 3 post-commit entries existed at that point). Two alternative candidates surfaced from this run's grep:

1. **The f6fbb7e commit body lists 5 included files** (STATE.md, QUEUE.md, NEEDS-INPUT.md, PROPOSED.md, JOURNAL.md). The commit covers 5 files, +166/-35. Pattern-matching "5 files in the commit" → "5 commits behind" is a plausible micro-confabulation.
2. **`research/2026-04-30-push-mystery.md` line 51 contains the literal string "worker-10am commits (5 commits, `76e211b` … `96aab20`)"**, referring to a 2026-04-29 worker chain. Worker-11am 2026-05-01 may have read this research file (the role spec doesn't require it but doesn't forbid it) and pattern-matched the "5 commits" phrase.

Neither candidate is provable from on-disk evidence alone. Both fit the broader pattern: the "5" was generated by linguistic pattern completion against a nearby "5"-shaped fact, not by running `git rev-list`.

## Recommendation

**Actionable change.** Two refinements to the cowork-session 2026-04-30 PROPOSED entry, building on yesterday's four sub-amendments. **No new PROPOSED entry needed.**

1. **Expand the entry's scope from "auditor" to "auditor + worker + planner".** The on-disk evidence shows the worker-11am 2026-05-01 11:00 originated the wrong number, not the auditor. A corrective scoped only to the night-auditor role would not have caught the entry that actually produced this confabulation. The four sub-amendments yesterday's researcher proposed (content parity not byte parity, numeric self-consistency, full `git status -s` reporting, timezone discipline) apply equally to the worker role's `verified:` block and the planner role's STATE.md "Known constraints" section, where commit-distance / byte-count / file-state claims are routinely cited. Suggested wording change: replace "auditor" with "any role making quantitative claims" in the corrective text.

2. **Validate the corrective is working at the workers/digest layer; the auditor remains the one open gap.** Empirically, every 2026-05-02 worker entry, the digest, and today's 2026-05-03 night-auditor audit verified `git rev-list --count origin/main..HEAD == 1` directly and cited the bash command output. The discipline holds when applied. The single remaining failure was upstream of the corrective: auditor-4 (2026-05-02 00:05) confabulated and the wrong number sat on disk for ~7h before the researcher caught it. The corrective doesn't need new tooling; it needs to be applied at the audit layer (where it currently isn't) before the next confabulation slips through. The priority bump from P2 → P1 yesterday's researcher recommended is consistent with this evidence.

This research file is supplemental grounding for those amendments. Eric (or the next planner) should fold both into the existing cowork-session 2026-04-30 PROPOSED entry's "What it would do" bullet during the next evening review.
